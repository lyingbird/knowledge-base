# 单图到游戏角色资产的自动化管线评估

> 评估「一张静态立绘 → 游戏可用的动态 2D 角色资产、且尽量低成本/少手动」是否可行。**最终结论：可行且已端到端实测验证**——`角色图 → see-through 自动拆层 → 自动/手动绑骨 → Godot 引擎内部件级动画`。但有强输入约束：see-through 只在「标准站姿、单角色、手臂可见」上效果好，对夸张造型/多主体会崩。零手动 + 高表现力目前不成立；自动管线产出的是待机/转头/眨眼/口型这一档动效。完整链路三段（拆层 / 绑骨 / 进引擎动画）均已在本机 RTX 4070 Ti SUPER 上跑通。

## 目标

把单张动漫立绘变成游戏里能用、表现好的动态角色资产，且本人尽量不做手动调整。

## 链路与逐段成色（2026-06-14 核查）

| 环节 | 工具 | 自动化 | 关键事实 |
|---|---|---|---|
| 拆层 + 补绘 | see-through | 全自动 | 单图 → 最多 23 层补绘 PSD。省掉美术数小时手动拆件，是全链最值的一步。 |
| 自动绑定/形变 | StretchyStudio（github.com/MangoLion/stretchystudio，editor.stretchy.studio；免费/开源/网页，专为 see-through 模型做） | 半自动 | 实测：拖入 see-through PSD →「17/17 层匹配」→ 网格化 + 自动骨架（含 AI Auto-Rig DWPose）→ 可选微调关节。**导出已实测确认**：Spine (4.0+) / Live2D Project / Live2D Runtime⚠️ / PNG 帧序列（透明、可调 FPS、ZIP 或文件夹）。 |
| 眨眼/口型材料 | PachiPakuGen → SpriTalk | 半自动 | AI 自动补帧（RIFE）+ 嘴部检测（SAM3），但需手动调图层可见性/顺序、切出手/耳、配元音。输出为给 SpriTalk 的分层 PNG，非标准引擎格式。需 DX12 + CUDA N卡。 |

## 核心判断

1. **see-through 的定位是「自动备料」，不是「一键出成品角色」。** 它自动化了拆件+补绘这段脏活，这是 2D/2.5D（[[游戏生产管线]]）的真实价值点。
2. **「零手动」目前不成立。** 最自动的 StretchyStudio 仍需 ~30 秒手动调关节；PachiPakuGen 需手动配层。see-through 作者明确声明它 ≠ Image-to-Live2D，专业绑定质量需美术手动 rig。现实是「轻量手动」。
3. **动态类型有限**：可得待机/眨眼/口型/木偶形变，非高表现力自定义动画；越自动表现力越平庸。
4. **进游戏引擎可行（判断已修正）**：StretchyStudio 实测可导出 Spine (4.0+)、Live2D（Project/Runtime）、透明 PNG 帧序列。Spine/Live2D 是 Unity/Godot/Unreal 的标准 2D 骨骼动画格式，PNG 序列则万能通用。所以"进引擎"不再是死结；真正的变量是**自动绑定的质量**——Live2D Runtime 导出带 ⚠️，作者也声明自动 rig ≠ 专业手 rig，高表现力仍需人工精修。
5. **仅 2.5D**：不产出真 3D 模型；3D 角色需求见 [[3D生成]]。

## 本机实测（2026-06-14，RTX 4070 Ti SUPER 16GB）

第一段（see-through 拆层）已在本机完整跑通并验证：

- **环境**：并存 Python 3.12 venv（`F:\see-through\.venv`）+ torch 2.8.0+cu128；核心管线只需 base `requirements.txt`，detectron2/mmcv/sam2 可选档全跳过。
- **模型**：LayerDiff 3D（~9.5GB）/ Marigold / SAM 直连 huggingface.co（走本机代理）自动下载，缓存于 `F:\video_digest\models\hf`。
- **实测基准（免 offload）**：1024 → ~3-4 分钟 / 17 层 / 峰值 ~12.4GB；1280 → ~6 分钟 / 18 层 / 16GB 未 OOM、更锐利。均产出 PSD + 深度 PSD + 带 alpha 分层 PNG + 重组图，重组与原图一致、遮挡区补绘完整。建议成品用 1280、迭代用 1024。
- **关键坑（已验证）**：16GB 卡上**绝不能用 `--group_offload`**——它把扩散从 ~2s/step 拖到 ~151s/step，后处理 23 层 VAE 解码卡死（实测停滞 2.5 小时无产出）。offload 仅适合 8-12GB 小显存。
- **下载坑**：hf-mirror.com 镜像对 resolve 链接返回 308、与 hf-xet 冲突，下载失败；本机有代理，直连 HF 正常。
- 操作手册见 `F:\see-through\RUNBOOK_pipeline.md`。

第二段（StretchyStudio 绑定）也已用浏览器实测验证：把上面产出的 PSD 拖进 editor.stretchy.studio →「**17/17 层匹配**」→ 一键导入并网格化 → 自动生成人形骨架（root/torso/neck/head/arms/legs/knees…，含 AI Auto-Rig DWPose）→ 进入关节微调向导。导出对话框确认支持 **Spine (4.0+) / Live2D Project / Live2D Runtime⚠️ / PNG 帧序列**（透明、可调 FPS、导出 ZIP/文件夹）。即 see-through → StretchyStudio → Spine/Live2D/序列帧 → 引擎 这条链端到端可行。

**复杂多主体素材实测（绿发和服角色 + 两只精灵）**：1280 跑通出 16 层 PSD，主角身体/脸/发/腿/和服补绘完整、可绑定。但暴露三条硬限制：① **姿势被标准化**——原图张开的夸张大袖被规整成下垂袍子（topwear），原始剪影丢失；② **配角被丢弃**——两只飘浮精灵未被捕获（objects/wings 层为空）；③ see-through 只认**单个标准角色**。对应工作流建议：多主体素材要**逐个裁切分别跑**（主角一张、每个配角一张），再在 StretchyStudio/引擎里合成；夸张服饰/极端姿势会被规范化，不适合需要保留原始造型张力的场景。

> 结论修正：① see-through 「自动备料」在消费级 16GB 卡上 **3-4 分钟/图**，实用性高于预期。② 「进引擎」不是死结——StretchyStudio 能导出 Spine/Live2D/PNG 序列。③ 真正的剩余变量是**自动绑定的质量**（高表现力仍需人工精修）+ **素材适配性**：简单单角色效果好，多主体/夸张造型需预处理或人工补救。

## 第三段实测：Godot 引擎内部件级动画（2026-06-14 验证）

把 see-through 的分层 PNG 直接在 Godot 4.6.3 里组装为**剪纸骨架角色**并验证可动：

- **环境**：winget 装 Godot 4.6.3；`.tscn` 是纯文本，可程序化生成（脚本 `F:\see-through\_gen_godot_rig.py`），无需 MCP。
- **结构**：各层全幅对齐 PNG（centered）按 PSD 层序堆叠；「颈部以上」编入头部轴心组（HeadBack/HeadFront 绕颈根 pivot 旋转），身体组保持，AnimationPlayer 驱动。
- **实测产出**：头部转动 + 头发摆动 + 呼吸的 idle 循环，Vulkan 实时渲染、无脱节（工程 `F:\godot_rig_demo`）。证明 see-through 分层 → 引擎内部件级动画 这一环可行。
- **关键认识**：Godot 2D 用 `Sprite2D` 节点层级 + 旋转做「剪纸/cutout 动画」即可（不必上 Polygon2D 蒙皮）；眨眼=切换眼睛层、口型=切换嘴层、转头=头部组旋转。能独立动的部位 = see-through 给出的独立层，所以**画图/选图时就要考虑可绑定性**。
- **Godot MCP**（可选，交互式编辑用，需重启会话才连得上）：[tugcantopaloglu/godot-mcp](https://github.com/tugcantopaloglu/godot-mcp)（149 工具）、[Coding-Solo/godot-mcp](https://github.com/Coding-Solo/godot-mcp)（经典稳）、[hi-godot/godot-ai](https://github.com/hi-godot/godot-ai)。

## 战略结论：低成本 2D 动画，这套行不行？

**行，且已验证可落地** —— 适合「批量做风格统一的角色待机/表情动效」（卡牌、gacha 立绘、视觉小说、轻量 RPG 角色动效）。三条必须守住的边界：

1. **挑图决定成败**：标准站姿、单角色、手臂可见、正面 → 自动流程好；夸张展开袖、多主体、复杂构图 → see-through 在拆层阶段就崩（脸糊、手臂丢）。能控制输入就能控制成本。
2. **动作复杂度有上限**：自动给 idle/转头/眨眼/口型；打斗、大幅肢体动作仍需逐骨手绑。
3. **可绑定性要前置设计**：手臂等部位能否独立动，取决于原图能否被拆成独立层——在画/选图时就要考虑。

不适合：拿任意高表现力 hero 立绘一键出战斗动画——它省的是备料，省不了核心绑定与手艺。
