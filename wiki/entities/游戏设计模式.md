# 游戏设计模式

> 借鉴建筑与软件工程的「模式」思路：把反复出现的设计问题与解法命名、归档，让团队用同一套词汇讨论，而不必每次从零发明。

## 两个不同源头的「模式」

同名但内容不同，引用时必须分清：

### 1. 玩法设计模式（Björk & Holopainen）

Staffan Björk 与 Jussi Holopainen，*Patterns in Game Design*，2005。来自学术界，目标是建立「游戏玩法」的通用描述语言。收录两百多个模式，按层级组织：游戏元素、资源与资源管理、目标与目标结构、游戏状态、动作与事件、规则、主题、信息、界面、叙事结构等。

模式的写法统一：名称、问题、解法、后果、相关模式。例如「Power-Up」（能力提升）描述的是「临时或永久增强玩家能力以制造爽感与节奏变化」，并指出其后果是会削弱挑战性。

这套模式的最大价值不是照抄，而是提供「这是什么」的命名能力。团队能说「这里缺一个 risk-reward 结构」而不是「这里感觉不对」。

### 2. 代码架构模式（Nystrom）

Robert Nystrom，*Game Programming Patterns*，2014（网络版免费）。这本是工程书，讲的是游戏循环、组件模式、双缓冲、对象池、状态机、观察者等实现层模式。与玩法无关，但游戏程序员的常识。

两者常被同名混淆，实际分别服务于设计师与工程师。

## 玩法模式的几个代表

| 模式 | 解决什么 | 代价 |
| --- | --- | --- |
| Risk/Reward | 让决策有张力 | 风险收益比失衡就变成必选或必避 |
| Power-Up | 制造阶段性强弱反差 | 削弱长期挑战 |
| Boss Monster | 提供阶段性的能力检验 | 制作成本高，复用性差 |
| Resource Management | 制造长期规划 | 新手认知负担 |
| Secret | 奖励探索 | 玩家不看攻略就找不到，投入白费 |
| Catch-Up | 缩小领先差距 | 削弱领先者的成就感 |
| Asymmetric Abilities | 制造角色差异与配合 | 平衡难度指数上升 |

这张表的价值在最后一列：模式本身没有好坏，代价必须被同时设计。

## 模式的正确用法

1. 作为诊断词汇：玩到某处感觉不对，用模式表定位缺了什么。
2. 作为沟通压缩：一句话顶一段解释，减少评审摩擦。
3. 作为创意触发器：把两个不相关模式强行组合，是常用的原型方法。
4. 不作为抄作业清单：知道有 Boss 模式不等于知道这场 Boss 该考什么。

## 模式的局限

- 命名覆盖不了体验。模式描述「结构」，不描述「手感」。有 Risk/Reward 结构的游戏可能依然难受。
- 会强化既有范式。模式库越全，越容易产出「什么都有但没特点」的设计。
- 学术版与工程版同名不同义，跨领域沟通需要先对齐。

## 与镜头的区别

[[设计镜头]]问「如果你这样看会怎样」，模式说「这样做通常能解决这类问题」。前者防止想错，后者防止重造轮子。成熟团队两者都用：先用镜头找到问题，再用模式找候选解法。

## 具体案例

### Collecting：一个模式能覆盖多少游戏

Björk 与 Holopainen 的模式页写法值得照抄。Collecting 的定义是玩家收集游戏中的物件，模式页里写明它可由 Collections、Drawing Stacks、Grind Achievements、Herd、Movement、Power-Ups、Rewards、Scores 这些模式实例化，可被 Camping、Crafting、Game Element Trading、Geometric Progression 调制。

页里给的两个例子是 Super Mario 64 与 Super Mario Sunshine：两者都围绕收集星星解锁新关卡并推进故事。第三个例子是 Pac-Man，它的主要动作是移动与吃豆，收集在这里退化成了核心动作本身，说明同一个模式在不同游戏里的权重可以差很远。

这种写法的价值在于它给出的是"这个模式能怎么被组合"，而不是"这样做才对"。

### Halo: Combat Evolved 的移除分析

2004 年一篇发在 HBO（halo.bungie.org）站上的分析论文用的就是 Björk 的五步法：先把 Halo 的主模式拆成组件找出底层模式，再假设把某个模式移除，看玩法会怎么变。

这个"移除"手法是模式分析里最实用的一步，因为它把"这个设计有什么用"变成可回答的问题：删掉它，玩家会失去什么。如果答不出失去什么，这个设计就是装饰。

### Grinding：一个负面模式为什么在 MMORPG 里是必需的

Björk 与 Holopainen 明确把 Grinding 归为负面模式，但同时指出它在 MMORPG 与 JRPG 里可能是必需的：它提供了节奏低谷，让高强度战斗有对照，也让社交时间有填充。

Player Elimination 同理，是负面模式，对应 Reiner Kramer 2000 年提出的设计准则 "No early player elimination"（不要让玩家在游戏早期就被淘汰出局，只能干看着）。

这两个例子说明模式框架里"正面/负面"不是好坏判断，而是体验后果的标注。

### 五个提取步骤：recognize / analyze / describe / test / evaluate

Björk 2003 年在 GDC 讲这套方法时强调 analyze 阶段要做的事：把模式从游戏里"移除"，再解释玩法会如何改变。这一步不能靠想象，需要真的改一版去测。

这也是这套方法没有被业界主流采纳的原因之一：它要求做实验，而工业流程更愿意直接抄现成的设计。

### 模式的四要素

Name / Description / Consequences / Using the Pattern / Relations。Relations 里分 superior patterns（上位模式）、subpatterns（子模式）、conflicting patterns（冲突模式）。

这套结构的实际用处是在评审时提供问答模板：这个设计的后果是什么？它属于哪个上位模式？它和哪些模式冲突？

### 为什么这套框架没成为主流

两个原因。第一，作者自己明确说模式不是给出唯一正确答案，而是描述可选方案并阐明权衡，这种"描述性而非规定性"的定位让它难以当作检查清单用。第二，有人担心模式会僵化创造力：一旦团队里有人说"这是 Collecting 模式"，讨论就容易停在标签上。

这与 [[设计镜头]] 的差别就在这里：镜头是问题（你有没有考虑过……），模式是分类（这属于……）。前者逼人继续想，后者容易让人停止想。

### 两个旁证项目

The 400 Project（Barwood & Falstein, 2003）试图定义 400 条设计师应当遵循的规则，例如 "Provide Clear Short-Term Goals"。它的命运与模式库类似：局部有用，整体难落地。

Game Ontology Project（Zagal et al., 2005）走的是另一条路：不做设计模式，做玩法本体的层级分类。它的用途偏学术分析，不偏生产。
