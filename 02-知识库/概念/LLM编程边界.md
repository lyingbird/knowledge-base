# LLM编程边界

> Jonathan Blow 对 LLM 编程的精确批评——不是"AI 不行"，而是"LLM 持不住约束"。与 Thomas Brush 的 Copilot 全天候生产力经验看似矛盾，实则可用 bug 分类学统一：LLM 能查 shallow state bugs，查不了 deep state bugs；两种经验不矛盾，取决于 bug 分布与代码库所有权。

## Blow 的核心论点：约束的保持

编程的真正难点是**约束（constraints）的保持**——坐标系统、玩法位置 vs 视觉位置的二分、实体序列化格式……每一行新代码都要与整个既存系统的隐式约定互操作。程序越大，这张"蜘蛛网"越密。

**LLM 持不住约束**：让它加函数它能加，但会静默丢掉其他系统依赖的旧约束；约束多了就顾此失彼。"它是个语言模型，不是棋手。你真正需要的是一个下棋的 AI。"——真正能编程的 AI 会更像 AlphaZero（自我博弈训练）配上 LLM 当对话接口的融合体。

## bug 分类学

- **shallow state bugs**：代码永远在做错事，看源码可见——LLM 能查。
- **deep state bugs**：数据/格式正确但触发了罕见代码路径组合，状态复杂——LLM 查不了。这是 Blow 自己最耗时的 bug 类型。

对 Brush 的 Copilot 生产力（一年修 1000 个 bug/feature）的解释：Brush 的 bug 恰好集中在 shallow 类（手柄抖动=类型转换时机这类），且 Brush 对自己 4 年手写的 Unity 代码库极熟，验收便宜。

## 迭代才是真问题

就算 one-shot 生成游戏成立，**迭代才是真问题**——"跳窗动作感觉黏"这种体验级反馈，AI 无从下手；人类需要一个可读的中间表示来定位问题。所以"可读代码作为中间层"在可预见的未来不会消失。

对游戏开发的推论：LLM 适合原型、工具链、shallow bug 清理；玩法手感与系统约束密集的核心代码，验收成本仍然由最懂代码库的人承担。

## 立场澄清

Blow 不反 AI，"有用就用"；反感的是**过度宣传**（excessive claims）。这与知识库既有页 [[LLM编码原则]] 的立场互补：Karpathy 一系总结的是"如何约束 LLM 编码 agent"，Blow 补充的是"约束本身为什么守不住"的机理解释。
