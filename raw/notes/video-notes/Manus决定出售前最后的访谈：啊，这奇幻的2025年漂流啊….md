## 0. 这节课在讲什么

这次访谈围绕 Manus 联合创始人兼首席科学家季逸超的三段创业经历展开：高中时代的 iOS 浏览器出海，2014 年前后围绕 NLP、语义搜索和知识图谱做 Magi，GPT-3 出现后退出原路径，再到 2024 年加入肖红团队并参与 Manus。核心并不是单纯复盘一家公司走红，而是借一位技术型创业者的视角，解释 AI 应用公司如何在模型快速演进、算力成本高、用户需求未定型的环境里做产品选择。

主线可以分成四层：

1. 个人能力与角色定位：季逸超从“自己当 CEO”转向“首席科学家 + 合适 CEO”的搭配，反复强调自己不适合商业化、管理复杂组织和处理人际复杂度。
2. 技术范式更替带来的创业判断：上一代 NLP 垂直整合路径被 GPT-3 击穿，形成他后来不轻易自训模型、不买“模型彩票”的关键经验。
3. Manus 的产品起源：Monica 是现金流、用户观察窗口和“空画布”，AI 浏览器项目被放弃后，Cursor 的跨人群使用现象启发了云端通用 Agent 的形态。
4. Agent 公司的经营逻辑：Agent 不是更聪明的 chatbot，而是“用户、模型、环境”三元系统；真正的难点在环境、沙盒、上下文工程、成本结构、用户高价值任务和商业化跑通。

标题中的“决定出售”在可读转写中没有形成明确讨论，正文不把它写成确定事实。

## 1. 逐段内容笔记

### [00:00:01-00:04:56] 开场：正常的 CEO、乔布斯病与 App Store 红利

开场先抛出两个判断：一是肖红“正常、身心健全、没有极端思想”在 AI 创业圈反而稀缺；二是许多创始人“没有乔布斯的命，却得了乔布斯的病”。这句话既是在评价行业里的偏执型创始人，也是在回看季逸超自己过去做 CEO 的不适配。

季逸超的家庭背景被放在“科学家父亲 + 中关村创业者母亲”的夹层里解释。他小时候不是传统意义上的学霸，但很早开始自己捣鼓软件。2009 年前后 App Store 出现，使个人开发者具备全球化变现能力。对一个高中生来说，App Store 给了课外爱好一个第三方指标：能赚钱，能向父母、同学、老师证明价值。

他做的第三方 iOS 浏览器采用 buy-a-copy 模式，每卖一份收一份钱，维护成本较低，后来累计赚到一笔可观现金流。[00:03:11-00:03:47] 这段经历被归因于移动互联网早期的“蛮荒期”：硬件媒介变化后，巨头和个人开发者在新平台上一度相对平等。AI 时代则不同，技术突破没有伴随一个全新硬件平台，巨头、创业公司和个人开发者反应都很快，窗口期更短。[00:04:34-00:04:53]

### [00:04:56-00:10:47] 第一段产品：浏览器自然死亡，NLP 成为真正起点

高中浏览器不是以明确的“创业结束”收尾，而是逐渐成为下一段创业的起点。国内支付不成熟，国际信用卡限制了国内付费；他选择把自己的软件破解后发到国内论坛，把国内用户当作口碑传播。随后在中关村活动中接触真格基金，拿到 term sheet 后决定不上大学、开始创业。[00:05:14-00:07:12]

浏览器商业模式很快遇到变化：第三方 iPhone 浏览器玩家增加，巨头回归，付费买断模式开始走向免费 + 增值。团队尝试在功能上做跃进，围绕弱网环境下“预测用户下一次点击”做预加载，由此进入 NLP。[00:08:23-00:09:05]

浏览器最终因无人维护、iOS 系统迭代兼容性问题而从 App Store 下架。回看这件事，浏览器从古至今都更适合有分发渠道的巨头，而不是创业者以颠覆者姿态硬做。[00:09:31-00:10:47]

### [00:10:48-00:28:10] 第二段创业：Magi、语义搜索、知识图谱与 GPT-3 冲击

第二段创业始于 2011 年后对 NLP 的兴趣。2013 年 word2vec 论文出现，让自然语言文本更可靠地转成稠密向量，打开了把深度学习方法用于 NLP 的大门。季逸超当时把语义搜索想象成下一代 Google：如果可穿戴设备、语音界面和小屏幕成为未来，传统“输入 query、返回十个蓝色链接”的搜索交互就不够紧凑。[00:11:00-00:13:23]

Magi 的技术目标是把网页中的自然语言转成结构化知识，再以更紧凑形式回答用户问题。知识图谱当时严重依赖人工编辑，行业知识图谱还依赖咨询公司和专家标注；团队想做开放式信息抽取，把实体、属性和关系自动抽取出来。[00:14:27-00:17:20]

这条路被称为“最苦的一条路”：模型、产品、搜索引擎基础设施、爬虫、索引、预训练都自己做。NLP 技术范式从 dependency parsing、word2vec、LSTM + attention、Transformer 到 BERT 快速变化，每次底层技术迭代都让前期积累大幅折损。团队曾从预训练开始做两个约 0.3B 模型，2018 年前后还解决过当时意义上的 16K long context。[00:17:44-00:20:00]

GPT-3 early access 成为“天塌了”的时刻。他用简单 prompt 测试同类任务，发现 GPT-3 与团队自训端到端模型接近五五开。更大的冲击不只是单点效果，而是通用模型会继续下降成本、提升能力，垂直 NLP 公司多年的专用积累失去战略位置。[00:20:43-00:22:15]

他随后卖掉公司，去真格工作一段时间，接触了从用户需求到 benchmark 的量化方式，也看到了 To B 公司的经典难题：如何把用户收益转成可衡量指标。[00:26:53-00:27:18]

### [00:28:10-00:41:35] 加入 Manus 前的选择：不去模型公司，寻找空画布

ChatGPT 出现后，季逸超把 AI 产业粗略分为模型层、基础设施层和应用层。他几乎和所有大模型公司聊过，但不想去自己不用的产品，也不想再做垂直整合模型。他认为 ChatGPT 的成功是天时地利人和，并不代表每个模型团队都能自然长出好产品。[00:28:10-00:30:41]

他明确意识到自己不适合做 CEO：不喜欢商业化，不喜欢管理人，也容易在“赚钱方向”和“技术兴趣方向”之间毫不犹豫地选技术。理想位置是找一个更适合的一号位，自己在一个尚未定型、可以探索的画布上工作。[00:31:04-00:32:56]

Monica 让他感兴趣，是因为它作为 Chrome 插件没有改变用户习惯：用户仍然在 Gmail、YouTube、文档等原有场景中工作。功能分发基于 context，视频理解只在视频场景出现，文档改写只在邮件或文档场景出现。这种形态缓解了“每增加一个功能都会稀释其他价值”的产品复杂度问题，也成为观察用户如何使用 AI 的窗口。[00:33:45-00:35:03]

他评价 AI 创业更像传统制造业：不像移动互联网那样边际成本接近零，而是随着用户量增长产生线性成本。没有优化时，用户越多 token 和算力消耗越高，因此对经营、成本、操作能力的要求比上一代移动互联网更高。[00:38:58-00:39:29]

关于“模型公司和应用公司”的边界，他的判断是未来头部应用公司也会有做模型能力，头部模型公司也会做应用。但初期做模型会拖慢产品迭代，产品已经有 PMF、状态相对稳定后，再为了稳定性、降本或突破天花板去做模型更健康。[00:40:00-00:41:35]

### [00:41:36-01:05:46] 团队、浏览器项目与放弃浏览器

AI 创业里“身心健康”的价值在于受挫后能冷静站起来，而不是靠执念蛮干。季逸超 2023 年底开始和肖红团队接触，2024 年 3 月正式加入。同期他也看过许多大模型公司，比较欣赏几家团队的技术扎实、开源、品味和 evaluation 体系。[00:41:36-00:46:27]

2024 年 3 月到 9 月，团队一度围绕 AI 浏览器展开。逻辑并非凭空想象：Monica 已经有用户和正向现金流，团队认为自己可能是当时最懂用户在浏览器里用 AI 的团队。但插件生态有天花板，头部插件也只能覆盖 Chrome 用户的一小部分，许多普通用户甚至不知道浏览器插件是什么。[00:49:08-00:50:54]

他们做出内部可用浏览器后发现问题。浏览器历史上的重大替换往往依赖分发，IE 依赖预装，Chrome 依赖性能、生态和 Google 分发。用户是否会因为 AI 主动换浏览器，并不确定。Arc 创始人宣布 discontinue Arc 的原因也触发共鸣：一款优秀浏览器很难说服亲友迁移。[01:00:32-01:01:40]

于是 2024 年 9 月、10 月团队放弃浏览器项目。这并不被描述为失败，而是延续了“不要替用户决定未来形态”的思路：技术积累可以迁移，产品形态必须重新寻找。[01:05:40-01:05:46]

### [01:08:29-01:18:36] Manus idea：从 Cursor 的非程序员用法到云端通用 Agent

Manus 的 idea 来自一个观察：公司里许多非工程师也在用 Cursor。运营同事用它写博客，数据分析同事用它做分析和可视化。他们并不看左侧代码，只是在右侧不断和 AI 交流，让 AI 以编程或代码为媒介完成非编码任务。[01:08:54-01:09:39]

这带出一个关键判断：编程不是垂直能力，而是解决通用任务的媒介。Cursor 的 IDE 形态并不适合非工程师，因为它跑在本地、需要用户持续注意、会暴露代码和权限细节。更适合的形态是云端运行、可以并发、把代码作为工具而非主要呈现，并面向 prosumer 或高价值脑力工作者。[01:09:41-01:11:14]

团队此前做浏览器积累了 Chromium、自动化和调度系统能力，于是把“浏览器里的浏览器”搬到云上。内部代号被称为 browser in browser in the air。2024 年 9 月底开始做，2025 年 1 月中基本完成，但选择等到更适合 agentic 能力的模型迭代一起发布，以享受模型代际提升的溢出。[01:11:14-01:12:49]

Manus 的几个早期 bet：

1. 相信“通用 Agent”这种形态可以被做出来。
2. 不急于自训模型，而是押注 context engineering 和 Agent 框架能弥补当时模型不足。
3. 不做中国版 Cursor，而是服务有高价值任务的非程序员或 prosumer。[01:18:36-01:21:40]

### [01:21:40-01:31:55] 通用 Agent 的理由：不做什么、长尾任务与三元系统

AI 提升了创业公司产能，也让机会显得过多，因此“不做什么”变得格外重要。Manus 被描述为一款相对克制的产品：其他 Agent 公司可能不断增加工具，Manus 团队则经常问“能删掉什么”。[01:21:40-01:22:31]

选择通用 Agent 有技术和产品两层理由。技术上，Manus 是通用模型加一台计算机；每个 session 背后有独立隔离的虚拟机沙盒，而虚拟机理论上能运行多种算法。底层供给本身是通用的，做垂直反而是在上面增加约束。[01:22:43-01:23:47]

产品上，通用形态允许用户以自己的想象力使用产品，团队再根据集体行为发现头部场景。早期并不预设用户应该做什么，后来发现用户喜欢做 slides、网页、批量文件处理，再由产品团队做最后一公里优化。[01:23:47-01:24:44]

通用能力还服务长尾任务。普通 deep research 产品在头部问题上可能收敛，但 Google 之所以胜过其他搜索引擎，在于长尾 query 的惊喜。Manus 的例子是某个分子生物学家的实验仪器导出小众数据格式，系统能先研究格式、去 GitHub 找开源项目解析，再继续完成分析。这类任务对大众是长尾，对个人却可能是高频工作。[01:24:49-01:26:17]

Agent 被定义为三元系统：用户、模型、环境。Chatbot 只有用户和模型往复交互；Agent 多了环境或 runtime。Manus 选择虚拟机作为通用环境，并通过一次性沙盒、scale out、多沙盒并行、Windows 支持、预装工具和自维护的 Agent 发行环境来扩大动作空间。[01:28:08-01:31:00]

### [01:31:00-02:08:40] 成本、模型影响力、主动性与“通用 Agent”命名

Manus 虽不自训基础模型，但因 token 消耗量巨大，成为多个模型厂商的大客户，从而能用需求反向影响模型发展。用户付费转成 token 消耗，再转成对模型厂商的影响力。发布初期利润为负，但通过技术迭代、成本优化和商业化，接近打平或转正。[01:31:00-01:31:55]

Agent 成本结构与 chatbot 不同。Chatbot 通常用户和模型交替，输入输出比例相对可估；Agent 会持续自我工作，React 式上下文 append-only，每一轮都可能携带越来越长的上下文，输入 token 消耗巨大。这解释了为什么 Agent 定价更贵，也解释了为什么邀请码不是纯营销，而是算力和模型供应无法短期承接需求时的控量机制。[02:13:01-02:16:48]

未来 Manus 更关注 proactiveness，即主动性。当前 Agent 输出已经不只是一段话，而是一系列 action 或产物，但起点仍是 prompt。用户输入 prompt 本身很费劲，也无法自然携带足够上下文。主动性方向希望 Agent 在用户醒来前就基于 Notion、会议记录、招聘系统等上下文完成候选人评价草稿，只让用户确认。[02:02:20-02:04:28]

“通用 Agent”这个词并非精密市场定位，而是在发布视频制作中临时拍脑袋定下的技术性命名。后续对用户沟通会更按场景表达：企业关注 internal tools，普通用户关注网站生成、slides、文件处理等。通用架构的意义在于不同场景共享上下文和记忆，垂直能力之后还能“多做一步”。[02:04:40-02:07:37]

Manus 与垂直产品的关系不是简单替代。设计类 Agent 会服务专业设计师，Manus 服务有设计需求但非设计师的用户；同时也可以通过 Connector 或 Integration 串接 Notion、Microsoft、专业设计工具、招聘系统等服务。价值不只在节点，也在节点之间的边。[02:07:40-02:08:40]

### [02:12:33-02:27:49] 发布争议：邀请码、营销、定价和融资压力

发布后的核心争议是邀请码和过度营销。邀请码的解释是控量：发布前团队和云厂商、推理供应商沟通后发现，世界上第二天能立即到位的算力远少于想象；推理供应商甚至提醒不要放开，否则服务会挂。邀请码因此成为控制用户进入速度的手段。[02:12:33-02:14:48]

团队也承认邀请码机制有更好替代方案，比如定向邀请；邀请码被炒卖是他们没有预料到的副作用。大约不到一个月后，随着云厂商和模型厂商准备好 Agent workload，邀请码被去掉。[02:16:40-02:21:17]

关于“是否付费宣传”，季逸超给出强烈否认：国内热度对一个海外 prosumer 市场产品没有直接好处，反而带来压力。国内传播更多来自朋友、自媒体和多年“广结善缘”的自然支持；海外传播则依赖高价值用户、技术圈意见领袖先用起来，再自上而下扩散。两边传播链路被描述为基本不重叠。[02:17:41-02:20:23]

关于“贵”，解释来自成本结构：Agent 本质更接近按量付费，基础订阅只是门槛。海外用户对生产力工具付费意愿更强，而 Agent 本身非常贵；能不能通过定价、成本优化和商业化把产品跑通，决定公司能走多远。[02:21:18-02:27:47]

### [02:30:36-02:59:53] Agent 技术判断：chatbot 分层、上下文工程、MCP 与模型建议

Chatbot 和 Agent 的差异不完全由能力决定，而由用户群和任务类型决定。所有人都有 chat 需求，但 Agent 用户更集中在愿意为高价值任务付费的人群。ChatGPT Agent 出现后，Manus 把市场看成分层：低价、快速问答仍然属于 ChatGPT 心智，高价值异步任务则是 Manus 长期要服务的人群。[02:00:00-02:01:40][02:30:36-02:31:00]

过去大半年最重要的技术决策包括：

1. 没有盲目追 reasoning model。朴素 reasoning 可能增加 instruction following 问题和事实幻觉，Manus 采用单独 planning stage。
2. 对 MCP 保守。动态发现和卸载工具会污染 action space，并降低缓存命中率，进而影响成本，因此研究了不把 MCP 原生放进 action space 的调用方法。
3. 持续投入 context engineering，包括文件系统如何使用、上下文如何 offload 与 retrieve。
4. 承认早期对小模型有过过度期待，后来发现参数量仍然重要，知识、记忆、泛化能力很难彻底分离。[02:51:52-02:54:26]

online learning 被拆成三件不同问题：狭义上持续改变参数的在线学习；mass personalization，大规模个性化；continuous/lifelong learning，即任务分布随时间变化的持续学习。对于个性化，不一定要参数化，可以用 prompt 和 in-context learning 动态注入；对于代码补全这类理想分布不随时间变化的任务，更像 on-policy 数据收集和周期性优化，而不是严格在线学习。[02:55:22-02:57:56]

对模型厂商的建议集中在 Agent 工况：不只是扩大 context window，更要让模型具备 compaction awareness，知道上下文可能被压缩；推理要结合工具和 observation，而不是只做“缸中之脑”式 reasoning；模型要适应用户随时插嘴、改变目标、补充信息或终止任务的异步交互；还要提升 error resilience，在真实环境出错后能恢复并寻找替代路径。[02:57:57-02:59:53]

### [03:00:18-03:30:58] 全球竞争、组织、AI 未来与行业格局

这次创业与前两次不同：成本更高，发布第一天就可能烧掉大量算力；同时也是真正参与全球竞争，有一种“从 CBA 到 NBA”的感觉。即便达到很高收入规模，放到全球 AI 头部选手里仍只是平均水平，需要继续学习。[03:00:18-03:01:06]

组织上，产品和技术的关系是“技术服务产品，但有一票否决权”。如果产品为了快而放弃“纯血 Agent”思路，技术会阻止。团队不喜欢投票，因为投票会让人服务自己的立场；更重要的是围绕同一目标提出足够多 alternatives，再由 CEO 拍板。[03:04:01-03:05:20]

AI 对组织结构的改变没有想象中大，但让组织中多了许多 AI。公司鼓励员工使用并报销各种 AI 产品，不只限于自家产品，因为 AI 公司首先要让员工理解业界前沿。AI 还没有到替代岗位的状态，但能让个人生产力成倍提升。[03:05:33-03:06:13]

模型竞争没有终点，这也是季逸超不做模型的原因。AI 产品竞争的稳态也不清晰，因为移动互联网的稳态来自用户时间被瓜分完，而 Agent 的努力方向是减少与用户直接交互的时间、在后台创造价值，不再以用户注意力时长作为主要约束。[03:08:39-03:10:58]

2026 年 Agent 会进一步爆发，但形态可能不是更多 C 端娱乐，而是渗透到更大人群、从提效工具变成主要生产要素。隐忧不是竞争本身，而是产品复杂度：每增加一个东西都会稀释其他东西。如果因为竞争而死，说明产品已经很好；更大的风险是失去独有价值、为了增长堆功能。[03:12:39-03:16:24]

对海外模型厂商的判断：OpenAI 仍有诞生新范式的创新文化，但需要平衡产品目标和研究自由；Anthropic 在开发者社区、MCP、Claude Code 等方面有根基，优化目标更贴近高经济价值任务；Google 在预训练、多模态、数据和搜索索引上有长期优势；xAI 更像在押注 pixel in, pixel out 和差异化基础设施；Meta 在杨乐坤离开后可能减轻思想负担，转向更快见效的工作。[03:16:24-03:19:16]

最后的判断落在“AI 接下来的进步需要用户的参与”。模型、环境、产品和用户使用方式共同推动 Agent 从 buzzword 变成生产要素。[03:30:54-03:30:58]

## 2. 核心概念

### App Store 蛮荒期

移动互联网早期，硬件媒介变化带来新平台，巨头和个人开发者都要重新适应。个人开发者能凭借 App Store 直接全球变现，出现短暂的“众生平等”。AI 时代没有同等的新硬件平台，巨头和创业公司反应速度接近，因此窗口期更短。

### 垂直整合陷阱

模型、产品、爬虫、索引、infra 全部自研，在技术快速演进期会拖慢迭代，并让每次底层范式更新都冲掉前期积累。Magi 的经历提供了反例：GPT-3 使专用 NLP 模型的战略价值被通用模型吞没。

### 空画布

一个已有用户和现金流、但功能未完全定型的产品容器。Monica 作为浏览器插件，不改变用户习惯，靠 context 分发功能，让用户真实行为自然浮现。空画布不是无方向，而是用用户行为代替创始人拍脑袋。

### Context 分发

功能不靠主菜单堆叠，而是在用户所处环境中出现。YouTube 场景出现视频理解，Gmail 或 Docs 场景出现写作和改写。这样可以增加功能而不显著增加用户的认知负担。

### 通用 Agent

通用模型加通用计算环境。Manus 的每个 session 背后有独立沙盒和虚拟机，能搜索、运行代码、使用浏览器、调用工具、处理文件并生成产物。通用不是“什么都泛泛做”，而是让不同场景共享上下文、记忆和执行能力。

### Agent 三元系统

Chatbot 由用户和模型构成；Agent 多了环境或 runtime。环境决定 Agent 能触达外界的边界，模型决定智能水平，用户决定目标、上下文和反馈。真实产品竞争不是单纯模型能力，而是三者适配。

### Wide Research

区别于 deep research 的深度单线研究，wide research 通过大量沙盒并行 scale out。适用于批量找人、找邮箱、整理多对象信息等任务，避免模型在长任务中懒惰、遗忘或质量衰减。

### Proactiveness

Agent 的主动性。不是每天推送内容占用用户时间，而是基于已有上下文主动完成后台任务，把用户从发 prompt、搬运信息和填表中解放出来，只留下确认、修改和决策。

### Vibe ARR

对收入指标的警惕。ARR 应基于 MRR 乘以 12，年付收入应按月摊销，而不是把某个月收来的年付全部算入当月。指标口径会决定产品 taste，也会决定团队行为。

### Compaction Awareness

Agent 长任务中上下文会被压缩，模型应理解这一点，并主动把关键信息写入文件系统、检索系统或其他可恢复位置。相比无限扩大 context window，知道如何 offload 和 retrieve 更关键。

### Error Resilience

真实环境里错误是常态，包括系统报错、权限问题、资源限制、网页变化、文件格式异常。好的 Agent 不应轻易放弃，而要能识别错误、恢复状态、寻找替代路径。

## 3. 论证链条

### 链条一：为什么不先做模型

前提：Magi 曾从预训练、产品、搜索和知识图谱全部自研，技术迭代一来，旧积累快速折损。  
观察：GPT-3 用通用 prompt 达到专用端到端模型接近效果，并且成本与能力会持续优化。  
判断：在产品形态和用户需求未稳定前，自训模型会把团队锁进慢迭代和“买模型彩票”。  
结论：Manus 初期不自训模型，把重心放在产品形态、Agent 框架、context engineering 和环境能力上；等 PMF 稳定后，再为降本、稳定性和天花板考虑模型。

### 链条二：为什么 Monica 能导向 Manus

前提：AI 应用时代没人真正知道下一代产品该长什么样。  
观察：Monica 不改变用户习惯，且能基于 context 分发功能，因此能更无偏地观察用户如何使用 AI。  
判断：比起直接下注某个垂直场景，先用空画布观察用户行为更稳。  
结论：Monica 提供现金流、用户洞察和实验土壤；浏览器项目虽被放弃，其技术积累继续迁移到云端 Agent。

### 链条三：为什么不是 AI 浏览器

前提：浏览器是高频入口，但历史上的替换多依赖分发和生态，不只是功能好。  
观察：插件生态有天花板，AI 浏览器也未必能让普通用户迁移默认浏览器；Arc 放弃原有路径强化了这一判断。  
判断：AI 能力不必绑死在本地浏览器形态上。  
结论：放弃独立浏览器，把浏览器自动化、Chromium 和调度能力转到云端，形成 browser in browser in the air。

### 链条四：为什么通用 Agent 不是垂直 Agent

前提：底层供给是通用模型和通用计算环境。  
观察：用户真实需求分布高度不确定，长尾任务对个人可能是高频高价值；垂直工具容易在频次、心智和上下文流转上受限。  
判断：在通用架构上观察头部场景，再做最后一公里优化，比提前把产品收窄更合理。  
结论：Manus 保持统一 Agent 框架，同时优化 slides、网站、批量文件处理等头部场景。

### 链条五：为什么 Agent 贵、邀请码必要

前提：Agent 与 chatbot 的 token 工况不同。  
观察：Agent 会连续工作，上下文 append-only，每轮输入量越来越大，还可能并发多个沙盒。  
判断：算力和模型供应短期难以承接突发需求，成本也无法按 chatbot 经验估算。  
结论：发布初期用邀请码控量；长期必须通过定价、缓存、模型选择、上下文压缩、工具调用和商业化优化跑通。

### 链条六：为什么 AI 产品竞争不等于注意力竞争

前提：移动互联网产品最终争夺用户时长，稳态来自注意力被瓜分。  
观察：Agent 的目标是减少用户直接交互，在后台持续创造价值。  
判断：用户时间不再是唯一瓶颈，AI 产品的稳态约束尚未明确。  
结论：未来 Agent 竞争会围绕高价值任务、环境接入、上下文、主动性和商业闭环，而不只是 DAU 或使用时长。

## 4. 学习批注

1. “不做什么”在 AI 产品里比以往更难，因为 AI 让团队看起来什么都能做。Manus 的克制不是少做功能，而是要求每个新能力能增强统一系统，而不是成为又一个孤立 feature。

2. 这次访谈最有价值的地方，是把“模型能力”从唯一叙事中拿下来。Agent 的完成度来自模型、环境、上下文、产品、成本和用户任务共同作用。只讨论模型榜单，很容易忽略真实工作流里的权限、文件、网页、错误恢复和付费意愿。

3. 季逸超对自己不适合做 CEO 的判断很清醒。技术型创业者常把“我能看见技术方向”误当成“我能经营组织和商业化”，这次访谈把两者拆开了。首席科学家不是 CEO 的降级版本，而是另一种更适配的位置。

4. “模型公司会做应用，应用公司也会做模型”这个判断需要分阶段看。早期应用公司用外部模型提高速度合理；当成本、供应稳定性和差异化成为瓶颈后，模型能力可能重新变成必要资产。关键不是做不做模型，而是什么时候做、为哪个问题做。

5. Manus 对邀请码和营销争议的解释有内在一致性，但仍需要外部验证。尤其是“没有付费宣传”“海外传播链路独立”“不到一个月去掉邀请码”等说法，都属于当事人叙述，不能当作已证实事实。

6. “AI 像制造业”的说法很醒脑，但也有边界。Agent 成本确实随任务和用户增长，但模型价格、缓存、蒸馏、硬件效率和任务路由都可能改变成本曲线。它不是永远线性增长，而是在早期和高价值任务中表现得更像重资产服务。

7. 访谈里反复出现的“高经济价值用户”透露出 Manus 的真实定位：不是把 Agent 普及给所有人，而是先服务愿意为高价值工作付费的人。这解释了为什么它可以接受较高价格，也解释了为什么它不急于与 ChatGPT 抢最广泛的聊天入口。

## 5. 可复用知识

### 产品探索

- 先找“空画布”，不要急着定义最终产品。已有初步 PMF、现金流和真实用户行为的容器，比创始人的直觉更可靠。
- 功能分发尽量基于 context，而不是把所有能力塞进一个菜单。
- AI 时代的产品团队要持续问“不做什么”，因为产能扩大后，功能膨胀会更隐蔽。
- 通用产品可以先让用户自由探索，再根据头部场景做最后一公里优化。

### 技术选型

- 技术快速上升期慎做深度垂直整合，尤其不要在需求未定型时绑定自训模型迭代。
- “壳”不必然低价值。Agent 的壳包含 runtime、环境、工具、文件系统、上下文管理、错误恢复和成本优化，厚度远超 chatbot UI。
- 不要只追 long context，更要让模型知道上下文会被压缩，并学会写入、检索和恢复。
- 工具越多不一定越强，action space 污染、缓存命中率下降和成本上升都是真问题。

### 商业化

- ARR 口径要严谨，年付收入按月摊销，避免用指标骗自己。
- Agent 定价不能照搬 chatbot，因为 token 工况、并发、沙盒和长任务成本结构不同。
- 高价值用户更愿意为真实产出付费；低价问答和高价值异步任务属于不同市场层。
- 现金流产品可以为探索型产品提供时间和心理安全垫。

### 组织与角色

- 技术服务产品，但技术对破坏长期架构的短期 fix 应有否决权。
- 不要用投票替代共识。目标统一后，关键是提供更多 alternatives，让最终拍板更有质量。
- 技术创始人要识别自己是否适合管理、商业化和组织复杂度；不适合时，找到合适 CEO 可能比硬补短板更好。
- AI 公司应鼓励员工使用多种 AI 工具，组织学习本身就是竞争力。
