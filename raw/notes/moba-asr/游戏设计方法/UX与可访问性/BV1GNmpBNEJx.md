所款免费游戏，无需付费会员即可体验。你可以在这场演讲后立即下载并开始游玩。我们将讨论在开发这款游戏时学到一些东西，基本上是在很短的时间内从零开始开发。我们将为你提出三个关键问题，你在开发下一款游戏时思考：你打算怎么建造它？你怎么知道这一切都能正常运作呢？那你一路上制造的混乱怎么办？我们是怎么构建它的？所以让我简单介绍一下我们游戏的构成。这是一个游戏的典型，主要用 C 语言编写，大部分游戏玩法都用自定义标记语言定义，支持空中更新。它采用客户端预测服务器权威的模型来保护游戏的完整性。我们的后端采用微服务架构，大多数服务器用 Haskell 编写，运行在 Node.js 上。我们使用 Fabricless 服务和 Lambda 来部署代码，所以基本上是一个无服务器的体验。Lambda 是我们的主要数据存储，我们使用 Redis 进行分析和数据仓库。最重要的是，在这次演讲中，我们用 GameLift 提供多人游戏服务。既然亚马逊已经宣布了用于云游戏的 GameLift，我们这里就只讨论 GameLift 服务器。那么我们为什么选择 GameLift？我们知道要驾驭全球玩家群体，为他们匹配满意的对手，并在玩家所在的任何地方大规模部署服务器，这将是一个挑战。我们还有一个固定的发布期和延期，它与电视第二季的播出时间挂钩。更有趣的是，这是我们工作室第一款真正的多人在线服务游戏，所以我们基本上没有任何基础基础可借鉴。所以我们不得不依靠 GameLift 来为我们的多人游戏架构提供坚实的基础，让我们能在很短的时间内完成构建。所以这有几个术语会帮助你理解我们今天要讨论的其他内容。舰队是一组配置相同的服务器，游于游戏。你可以把它看作是游戏的 C2 自动扩展组。Flex 是一个无游戏的匹配解决方案，你可以用 JSM 编写自定义匹配规则。游戏会话是在包含你的玩家的舰队上预特定游戏服务器进程的过程。然后专用服务器是我们对运行在舰队实例上的游戏代码的称呼。你可以在每个舰队实例上运行多个专用服务器副本，以最大化硬件利用率。这展示了我们服务器架构的高层概览。我们的大多数核心服务都运行在自己的 PC 中，身份验证、数据存储、遥测、事件管理这类东西。注意下面这条线，显示运行在游于游戏管理的 A W S 账户上的基础设施是用 GameLift 托管以 C2 模式。你只需上传代码 C 文件，托管服务会自动获取并部署到你选择的全球区域，然后为你启动服务器。由于这段代码运行在我们 VPC 外部的一个半信任环境中，我们对它保持一定的距离。两个半部分之间有两条主要连接。配对系统会将玩家分配到专属服务器，然后通过游戏事件系统将重要的游戏数据和结果流传回我们的系统，这样我们就能追踪统计数据，并基于玩家在游戏中赚取的奖励。那么让我们深入探讨一下配对系统。当玩家在手机上点击播放时，他会向我们的服务器发起一个 REST 调用，首先调用我们所用的原服务器，这是我们所有微服务的前端，然后他会依次调用我们匹配服务上的匹配器。由于我们的平台支持多个并发版本的游戏，每个客户端请求都包含其版本号。配对服务在数据库中查找版本号，以查看哪些游戏叶子资源与之关联。然后它向 Flex 系统发出开始匹配命令。Flex 找到匹配后，会根据你提供的规则，利用你在开始匹配命令中提供的客户端凭据来确定哪个区域应该托管这场比赛。GameLift 随后会预留一个免费的专用服务器实例，然后在你的代码上触发一个名为 OnStartSession 的事件。一旦触发该回调，我们的专用服务器就会自动初始化。当它准备好开始接受客户请求时，会调用激活游戏会话。完成所有这些后，GameLift 会向我们称为匹配做出力器 Lambda 函数触发一个事件，这样就会通过 WebSocket 通知该会话中的每个玩家，他们现在可以加入比赛了。然后一旦所有这些工作完成，就会进行匹配，启动一个服务器实例，创建一个游戏会话。所有基础设施都推出，你的玩家手机直接连接到专用服务器实例，提供非常低延迟的连接，让他们尽情享受我们的游戏。这是我们数据管道的高层概览。数据通过 P S 从我们的客户端和自有服务器流入。所有这些数据随后会经过一些自定义代码对数据进行增强、进行完整性检查，然后根据具体事件将其路由到一个或多个目标。离线分析的数据会被发送到 Redis，然后我们在这些数据上构建表格和报告。重要的运营数据随后通过 CloudWatch 发送这些指标，连接了 CloudWatch。我们有配置队和 Slack 系在监控这些告警。用于实时仪表的数据通过 P S 发送到 Lambda。这个数据管道对我们理解游戏是否真正有效至关重要。我们团队的笑话说什么都有匹配失败。当我们收到的半报告标题说匹配失败，半读了描述才发现实际上是无机加载失败。或者我们查看日志，发现服务器还没有完成部署。或者 Jenkins 构建失败了，所以没有可用的服务器来启动。你的手机过热是？因为你在用不支持的破旧设备玩吗？显然是配对出问题。意识到游于将选手纳入和排除竞赛的过程非常复杂，即使是工程团队成员也没有统一的语言来讨论这个过程实际上是如何运作的，以及它可能失败的所有方式。所以，我们创建了一个游戏体验图谱，为了建立这种共同的理解框架，也就是我们游戏的核心循环。我们从玩家第一次点击开始游戏那一刻起，绘制了一份详细的体验旅程图。我们绘制了每个屏幕的地图，以实现他们的所有具体技术步骤。然后我们定义了从每个步骤发出的指标和遥测数据，比如匹配开始、会话创建和匹配错误事件。我们在一个巨大的数据点电子表格中追踪所有这些数据。这样的话，我们就能准确看到哪里出了问题，这样我们就能快速修复，无论是在线还是在生产环境中。所以，如果我们早点定义这个，就能避免浪费时间去弄清楚什么才是真正的匹配问题。现在，我们如何理解来自这个遥测系统的所有数据呢？让我们来谈谈观测性。默认情况下，GameLift 提供了面向无错的表板来监控定位，它涵盖了你基础设施的基本技术支撑、游戏中多少玩家、有多少服务器、你不同地区利用率如何，诸如此类的东西。后来我们意识到，即使有内置表板，他们也没有告诉我们玩家实际上是如何体验游戏的。有明显的延迟吗？有像皮筋效应吗？我们实际上是在为玩家匹配高质量的队列。为了回答这些问题，我们基于游戏体验旅程中定义的遥测事件构建一系列表板。我们不能在这里全部讲述，但这里有几个例子。为了了解我们的玩家来自哪里，以便优化服务器布局，我们对每个玩家进行地理定位，并按国家地区跟踪关键指标，如玩家数量和延迟。这个图表显示了按原籍国分类的玩家数量历史。为了理解到我们无游戏服务器的延迟，先是平均延迟的折线图并不太有用，因为它掩盖了有趣的异常值，而且屏幕上满是无数个摘要图表，会让人感到不知所措。相反，我们发现将观察到的延迟分组到不同的区间或桶中，然后可视化这些桶中的玩家数量，这样更容易理解。我们可以按时间或地区绘制每个分段中玩家数量的图表，这样就能看出我们的匹配算法改进效果如何。对于你的游戏，你可以定义能为玩家提供最佳体验的延迟范围，然后你只需追踪有多少玩家落在这些范围内，而不用担心网络数据哪些进去而复杂的细节。现在，为了根据所有这些数据追踪如何改进我们的游戏，我们需要一个非常强大的日志系统。所以 Paris 会简单介绍一下我们如何处理日志以及围绕日志构建的工具。谢谢。以下是我们如何判断这不是配对问题的方法。GameLift 提供了多种简便方式，可以从 A W S 控制台获取特定会话的日志，但这些日志无法搜索。而且你需要知道游戏会话标识符才能检索日志。根据我们的经验，当服务器集群崩溃且没有游戏会话标识符可用时，你还需要一种方式来检索日志。我们在每个舰队实例上安装并配置 CloudWatch 来转发日志。最初，我们使用 O Observer 来搜索转发的日志，但日志量非常庞大，多次导致我们高配置的集群崩溃。这是在我们的开发和测试环境中。对生产来说，这既不划算也不可扩展。使用 CloudWatch 登录网站，我们可以在整个服务器集群中搜索日志，找出遥测技术无法显示的问题，包括服务器进程在游戏会话创建前失败的情况，或过去五分钟内有多少游戏会话已结束。这不需要额外的基础设施来管理。当服务器进程启动时，我们会为其提供关于该进程的唯一元数据，例如区域、游戏版本、实例 ID、主机名和端口。对于关键服务器事件，比如激活或结束游戏会话，我们会用其同时提供的元数据来丰富日志消息。在可能的情况下，我们还会用游戏会话 ID 来丰富日志。这些细节是日志与我们系统的其他部分相关联，让我们能够根据元数据搜索，快速查看正在运行的进程发生了什么。我们如何处理自己造成的混乱？直到我们在 GameLift 上运行了游戏的 MVP 版本，我们才清楚的了解如何管理游戏的构建和版本。对于我们的游戏，单个客户端版本可以兼容不同的舰队版本，这在我们需要制作新服务器构建来修复错误时很有帮助。尽早选择版本控制策略至关重要。我们没有，我们不得不回过头来改造我们的部署，确保系统中的所有组件都使用集中式方法来确定客户端应使用的 GameLift 资源版本。我们认为有两个 GameLift 资源需要与您的版本控制策略保持一致的命名：游戏会话列表以及匹配配置，因为它们将被用作用 GameLift 启动游戏的入口点。在按或 Amazon 自命名中包含版本号，这样可以轻松构建，无需进行额外查询来确定应使用的版本。该游戏要使用 Terraform 进行资源部署。然而，由于跨游戏版本共享 Terraform 资源所带来的挑战，以及为每个版本管理独立工作区的复杂性，Terraform 并未被用于创建版本 GameLift 资源。我们有一个要求，就是能够更新和删除某个游戏版本的资源，而不会对其它版本产生任何影响。最后，我们使用 A W S 开发工具包来建模游戏提升组件，为游戏的每个版本创建不同的 CloudFormation 配置。这样我们就可以放心的对某个游戏版本进行修改，而不会影响其他版本。我们的 C D K 高度依赖配置驱动。我希望团队中的每个成员都能够进行更改，而无需编写 C D K 代码。舰队实例类型、进程数量、每个舰队实例的配置以及位置信息都可以在配置文件中更新。由于我们需要快速调整匹配规则来改变玩家行为，我们构建了一个特殊的部署流程，能够在不中断玩家体验的情况下实时推送匹配规则更新。在开发高峰期，我们每天生成三十多个构建版本，这消耗了大量的资源，并产生了巨大的成本。在快速开发周期中，一周前的构建版本可能已经过时，不再需要了。我们在开发过程中构建了工具来清理旧版本的游戏。Step 队列来为我们站中的所有资源配合工作。Anywhere 队列允许你在任何地方定义 GameLift 资源。在这种情况下，是开发者本地机器运行服务器进程，这有助于更快的测试游戏功能，跳过冗长的部署过程，并快速获反馈。我们还花时间让开发者更容易生成 Anywhere 响应，特别是对于列出和描述舰队等操作，因为频繁进行这些 API 调用可能会昂贵。另外，实现强大的重试机制来处理速率限制。为远程连接舰队时，力准备不离破碎方法。在游戏运行时，能够运行它这样的命令，可以显示遥测可能遗漏的东西，比如游戏不同阶段中 CPU
